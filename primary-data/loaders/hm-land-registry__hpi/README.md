# 📈 Загрузчик: HM Land Registry — UK House Price Index (UK HPI)

Наполняет таблицу `"primary".hm_land_registry__hpi` месячными рядами UK HPI по
33 лондонским боро: индекс цен, средняя цена и **объём сделок**, плюс все
разбивки, которые источник даёт из коробки. Подключение к БД и пароль — в
[DB.md](../../DB.md).

Нужны `psql`, `curl` и `python3` (только стандартная библиотека).

## Как пользоваться

```bash
cd primary-data/loaders/hm-land-registry__hpi

./load.sh            # самый свежий доступный релиз
./load.sh 2026-07    # конкретный релиз, YYYY-MM
```

Загрузка занимает минуту: полная выгрузка ~35 МБ, после фильтра по Лондону
остаётся ~5 МБ. Имя файла релиза содержит месяц
(`UK-HPI-full-file-2026-07.csv`), поэтому без аргумента загрузчик пробует месяцы
по очереди от текущего назад и берёт первый, который отдаётся с кодом 200.
Релизы выходят с лагом примерно в два месяца: в октябре 2026 свежий релиз —
июльский.

Каждый запуск **полностью заменяет** таблицу (`truncate` + `\copy`), повторный
запуск безопасен. Догрузка «только нового хвоста» здесь была бы неверной: каждый
релиз пересчитывает предыдущие 12 месяцев. Если `Last-Modified` в источнике не
изменился, файл заново не скачивается.

Параметры подключения берутся из общего [db.env](../../db.env). Чтобы залить в
другую базу, переопределите `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER` в
окружении.

## Что загружается

Релиз 2026-07 — **14 607 строк**:

| Срез | `area_code` | Строк | Период |
| --- | --- | --- | --- |
| 33 боро (32 + City of London) | `E09000001`…`E09000033` | 12 507 | 1995-01 … 2026-07 |
| регион London | `E12000007` | 700 | 1968-04 … 2026-07 |
| England | `E92000001` | 700 | 1968-04 … 2026-07 |
| United Kingdom | `K02000001` | 700 | 1968-04 … 2026-07 |

54 колонки — ровно те, что в выгрузке, в том же порядке, имена переведены в
snake_case. Состав: общие `average_price` / `index` / `sales_volume`, разбивка по
типу жилья (detached, semi-detached, terraced, flat), по способу оплаты (cash,
mortgage), по типу покупателя (FTB — first time buyer, FOO — former owner
occupier) и по новизне (new build, existing resold). Что означает каждая колонка
и в каких единицах — в `comment on column` в [sql/ddl.sql](sql/ddl.sql);
первоисточник — раздел 8.2 «Format of data» в
[About the UK House Price Index](https://www.gov.uk/government/publications/about-the-uk-house-price-index/about-the-uk-house-price-index).

### Почему агрегаты оставлены

Рабочая гранулярность — боро, но три агрегата оставлены сознательно, и не только
«для нормировки»:

* **сезонное сглаживание есть только у них.** `index_sa` и `average_price_sa` в
  UK HPI публикуются на уровне стран и регионов (раздел 8.4 описания), на уровне
  боро эти колонки **всегда `NULL`**. Без `E12000007` взять сезонный профиль
  Лондона из этого источника вообще негде;
* **London / England / UK дают вложенную нормировку** — месячный спрос в боро
  осмысленно сравнивать с динамикой региона и страны, а не только с собственным
  прошлым;
* **обратный ряд с 1968 года** есть только у агрегатов (у боро — с 1995-го).

Great Britain (`K03000001`) и England and Wales (`K04000001`) **не** берём: это
промежуточные склейки, к паре London + England + UK они ничего не добавляют.
Цена вопроса — 2 100 строк на все три агрегата, то есть ничто.

Индексы отдельным файлом не выносим: таблица меньше 15 тысяч строк, первичного
ключа `(area_code, date)` достаточно, и он объявлен прямо в `ddl.sql`.

## Подводные камни

**Объём сделок отстаёт от индекса цен на два месяца — это не баг выгрузки.**
HM Land Registry намеренно не публикует `sales_volume` за два последних месяца
релиза, «чтобы не показывать заведомо недобранные объёмы» (раздел 8.6 описания).
В релизе 2026-07 проверено: `index` есть у всех 33 боро за 2026-06 и 2026-07, а
`sales_volume` за эти два месяца пустой у всех — ровно 66 = 33 × 2 пропуска.
Последний месяц с объёмами — 2026-05. Лаг пересчитывается при каждой загрузке:
`sql/verify.sql` печатает его в колонке «лаг объёмов, мес» и показывает хвост по
месяцам. Если значение перестало быть 2, политика публикации изменилась.

**Хвост объёмов не только обрезан, но и занижен.** Каждый релиз пересчитывает
предыдущие 12 месяцев вверх, по мере доезда регистраций: первая оценка месяца
строится примерно на 40% сделок, вторая — на 80%, третья — на 85% (раздел 4.4).
То есть последний год объёмов — систематически заниженный. Для обучения этот
год либо отбрасывается, либо досылка моделируется отдельно; дата выгрузки
фиксируется в `data/<файл>.csv.version`.

**`cash_sales_volume + mortgage_sales_volume ≠ sales_volume`.** Способ оплаты
известен не по всем сделкам, и источник это прямо оговаривает (раздел 8.6). В
релизе 2026-07 разбивка не сходится в 2 730 из 5 704 боро-месяцев, где обе части
непустые — то есть почти в половине. А вот
`new_sales_volume + old_sales_volume = sales_volume` сходится точно: 0
расхождений из 11 929. Обе проверки считает `sql/verify.sql`.

**Разбивки по покупателю и способу оплаты начинаются только с января 2012.**
`cash_*`, `mortgage_*`, `ftb_*`, `foo_*` до 2012-01 пустые: эти ряды строятся по
Regulated Mortgage Survey, а не по реестру. У боро это 175 непустых месяцев из
379. Объёмов по типу покупателя источник не даёт вообще — только цены и индексы.

**City of London — почти вырожденный ряд.** `detached_*` и `semi_detached_*` там
`NULL` за весь период (таких сделок нет), `terraced_*` заполнен рвано — 111
месяцев из 379, и последний из них 2024-12. Непрерывен только `flat_*`. Любая
модель, которая использует разбивку по типу жилья, должна это учитывать.

**`new_sales_volume` рваный и в середине ряда.** Регистрация новостройки требует
создания новой записи в реестре и идёт дольше (раздел 4.4), плюс в отдельных
боро в отдельные месяцы новостроек просто не продавали. По Лондону 578 пропусков
против 66 у `sales_volume`.

**База индекса — январь 2023 = 100**, а не 2015 год, как в старых публикациях.
Проверено: у всех территорий `index` за 2023-01 равен ровно 100. База меняется
при ребазировании индекса, так что число в комментариях `ddl.sql` надо
перечитывать после крупных методологических правок.

**С `hm_land_registry__price_paid` джойнится по коду, а не по имени.** В UK HPI
боро записаны по ONS (`City of Westminster`, `Barking and Dagenham`), в Price
Paid Data — капсом в колонке `district` (`CITY OF WESTMINSTER`). Джойнить надо
через `area_code` или через `upper()`.

**Дата в источнике — `DD/MM/YYYY`.** `\copy` выполняется с
`set datestyle = 'ISO, DMY'`; без этого 01/07/2026 уехало бы в январь. Все даты —
первое число месяца.

## Файлы

| Файл | Назначение |
| --- | --- |
| `load.sh` | определение релиза, скачивание, фильтр, заливка |
| `lib/check_header.py` | машинная сверка порядка колонок `ddl.sql` с заголовком выгрузки |
| `lib/filter_london.py` | отбор боро `E09......` и трёх агрегатов |
| `sql/ddl.sql` | схема таблицы и комментарии ко всем 54 колонкам |
| `sql/verify.sql` | итоговая сводка: лаг объёмов, сходимость разбивок, размер |

`\copy` грузит CSV позиционно, поэтому `check_header.py` вызывается **до**
заливки: если HM Land Registry вставит колонку в середину файла, загрузка
упадёт с понятной ошибкой, а не разъедется молча по типам. Соответствие имён
считается одним правилом, без списка исключений: `AveragePrice` →
`average_price`, `IndexSA` → `index_sa`, `FTBPrice` → `ftb_price`,
`Detached12m%Change` → `detached_change_12m_pct`.

Скачанные файлы лежат в `data/` — каталог в `.gitignore`.
